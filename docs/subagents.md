# エージェントの役割分担

このリポジトリで作業するときの分担。**決めるのはフロンティアモデルだけ**で、
手を動かすのは下位モデルという形に固定する。

| 役 | 誰が | やること |
| --- | --- | --- |
| 決断 | フロンティア（Opus / GPT-6 相当） | 要件の解釈、設計、タスク分割、契約（型・API・スキーマ）の確定、統合、受け入れ判断、マージ可否 |
| 実装 | luna（`gpt-6-luna` max）／ haiku | 指示された範囲のコードを書く。変更点の探索を含む中規模はluna、仕様が閉じた小さい変更はhaiku |
| 調査 | haiku | ファイル・呼び出し元・設定値の洗い出し、ドキュメントとコードの突き合わせ。並列に投げてよい |
| 検証 | haiku ／ luna | 型チェック・テスト・エミュレーターでの動作確認、再現手順の実行。実装した本人以外が担当する |

フロンティアは自分でコードを書いてもよい。分割の手間が変更そのものより大きいとき、
または一番risky な部分を切り出せないときは直接やる。

## 投げる前に決めること

フロンティアは下位モデルを起動する前に、次を固めてから渡す。固まっていないものを
渡すと、返ってきたものを捨てることになる。

1. 目的と「できた」の判定条件（通すコマンド、見える結果）
2. 触ってよいファイルと、触ってはいけない範囲
3. 変えてはいけない契約（型・APIのパス・DBのカラム・環境変数名）
4. 既知の落とし穴
5. 報告してほしい内容（変更したファイル・実行したコマンド・結果・残った不確かさ）

依存のあるタスクは同じ波に入れない。同時に走らせるのは互いに独立した 3 つまで。
同じファイルを 2 人に書かせない。エミュレーターは一度に 1 人だけ
（[../AGENTS.md](../AGENTS.md) の検証方針を参照）。

## 受け取ったあと

- 返ってきた報告は証拠ではない。差分を自分で読み、受け入れ条件を自分で再実行する
- 下位モデルの findings は裏を取るまで事実として扱わない（特に件数・網羅性の主張）
- 自分が書いたものを自分で承認しない。実装と検証は別のモデルに割る
- 失敗したタスクを同じ条件で同じモデルに再投入しない。原因を仕様不備／探索不足／
  タスク過大のいずれかに分類してから、ブリーフを直す・上位に上げる・分割する

## haiku に向かないこと

- 「何か問題はあるか」という開いた問い（止まる条件が無く、何も返ってこない）
- 件数や網羅性の保証（一覧は正しくても合計は合わない）
- 良い／悪いの判断、マージ可否

haiku には「一つのパターンの全件列挙」「指定した観点の抽出」「場所の特定」を頼む。
判断は必ずフロンティアが引き取る。
