# Issue #6: 共通処理の性能調査と改善

対象: https://github.com/YukkuriPannda/raku-bo/issues/6

比較元: `686163b`（develop）。計測日: 2026-10-21。

## 確認した原因と変更

1. `calcBalance()` が毎回 `refreshHeatmapWidget()` を呼び、105日分に必要な過去月を
   再取得していた。起動時の3ドメインの取得完了で3回走り、シフト・時給・予定支出だけの
   変更でも通信していた。草グラフ更新を今月の取引取得と取引変更の経路へ移した。
2. 4タブ、予定支出の2フォーム、手動入力が `useAppStore()` でストア全体を購読していた。
   使用するフィールドだけを選択し、複数フィールドには既存の Zustand `useShallow` を使う。

API、DBスキーマ、認証処理、残額の式、30秒の鮮度判定、force、ウィジェットの保存形式は変更しない。
過去月の追加キャッシュや新しい依存も導入しない。

## 再現できるストア計測

リポジトリのルートで実行する。Node v25.4.0、既存の mobile の TypeScript / Zustand を使用。

```powershell
node validation/performance/store.perf.cjs 686163b
node validation/performance/store.perf.cjs
node validation/performance/selectors.perf.cjs 686163b
node validation/performance/selectors.perf.cjs
```

`store.perf.cjs` は対象リビジョンの実際のストアを TypeScript で変換して実行する。
APIは1要求20ms、ネイティブ保存・通知・ウィジェットはスタブ、取引は架空のデータ。
本番API、DB、実機描画の速度ではない。`settledMs` はアクションと付随する模擬通信が
すべて落ち着くまでの時間で、タップから表示までの時間ではない。

各5回の中央値。全フローの値は [results.json](../validation/performance/results.json)。
今回の日付では105日を賄う過去月は3か月。

| 操作 | 全API要求 修正前→後 | 過去月要求 修正前→後 | settledMs 修正前→後 |
| --- | --- | --- | --- |
| 初期先読み | 12→6 | 9→3 | 43.76→44.90 |
| 30秒以内のタブ用再取得 | 0→0 | 0→0 | 0.06→0.09 |
| シフト強制更新 | 4→1 | 3→0 | 42.51→20.70 |
| 予定支出強制更新 | 4→1 | 3→0 | 40.95→20.81 |
| 取引登録 | 4→4 | 3→3 | 59.93→54.65 |

起動時は元から並列通信なので、この条件で初期表示の時間短縮は示せていない。
確実な効果は起動時の過去月要求が3分の1になり、無関係な更新での通信がなくなったこと。
取引登録の数msの差は測定ばらつきとして扱う。

自動チェックでは以下を要求する。

保存失敗・オフラインを意図して起こすケースでは警告ログが出る。終了コード0とassertの通過で判断する。

- 取引の追加・編集・削除・返済切替・予定支出完了で草グラフを各1回更新する
- シフト・時給・予定支出の取得・追加・編集・削除では草グラフを再取得しない
- 建て替えを草グラフと実質支出から除外し、残額を保つ
- キャッシュ保存が失敗してもAPI成功の結果を失わない
- 過去月の表示で今月の取引・残額・草グラフを変更しない
- 今月のforce取得とオフラインキャッシュへのフォールバックでも草グラフを更新する

`selectors.perf.cjs` は実際の画面ソースからセレクターを読み、Zustandの購読値を比較する。
無関係な `calendarEventsLoading` を100回変更すると、7か所とも購読値の変化は100回→0回。
各購読で使う計43フィールド・actionは、それぞれを変更して検知が続くことを確認する。
これはReactのcommit回数やCPUプロファイルではない。

## API / DB経路の確認

- `/transactions` の一覧は `items:transaction_items(*)` を含む1回の問い合わせ。
  明細取得を取引ごとにループするN+1はこの経路にはない。リレーションが使えない場合のみ
  明細なし取得にフォールバックする。
- 各API要求の認証で Supabase `/auth/v1/user` にアクセスする。過去月要求の削減はこの
  認証通信も減らす。認証のキャッシュ化や検証方式の変更は行っていない。
- `/shifts` はプロフィールの後でGoogle Calendarを呼ぶ。
  `/planned-expenditures` はユーザーの予定を取得して月をメモリ内で絞る。
  今回は実測せず、推測によるクエリ変更は行わない。

## Androidの確認

対象は `emulator-5554`、Android 16、`com.rakubo.app.debug` の既存dev client + Metro。
Dockerのmobileサービスを再起動した。リリースAPKやEASビルドは作らない。

```powershell
adb -s emulator-5554 reverse tcp:8081 tcp:8081
maestro --device emulator-5554 test .maestro/performance-smoke.yaml
```

`.maestro/performance-smoke.yaml` はMetro接続後、ホーム・履歴・シフト・支出予定を3周し、
各画面の表示をassertする。記録や予定の作成・削除、ログアウトは行わない。
実データを含みうるMaestroの成果物は一時フォルダーに保存し、コミットしない。

結果: 上記4タブを3周する全assertが成功（Maestro 2.11.0、終了コード0）。
dev clientの接続画面をアプリ本体と取り違えないよう、localhostの接続項目があるときは
選択してからホームの表示を待つ。支出予定のassertは固定の文字列ではなく実際の件数付きラベルを使う。

同じ成功実行で `dumpsys gfxinfo` をreset後に取得した1回分は349フレーム、
janky 316（90.54%）、p50 65ms / p90 93ms / p95 121ms / p99 250ms。
開発ビルド・エミュレーター・自動操作を含む参考値で、修正前の同条件の正常なキャプチャがないため
フレーム性能の改善とは判断しない。接続画面で失敗した実行のフレーム値も比較には使わない。

独立レビュー: Claude Code `--model opus --effort high`、完了JSONの
`modelUsage` は `claude-opus-5-5`。変更による新規ブロッカーなし。
レビューでは実行していないため、型・ストア・購読・Maestroの検証は統合側で別途実行した。

## 残る検証と既知の範囲

- 実機の操作時間、認証済み本番API/DBのレイテンシ、リリースバンドルサイズ、
  React/HermesのCPU・commitプロファイルは未計測。模擬通信の改善率を実機の改善率にしない。
- 取引変更後の過去月取得は引き続き毎回走る。返済切替も従来どおり更新する。
- 日付が変わってからシフト・予定支出タブだけへ復帰した場合、草グラフの日付窓は
  次の今月取引取得まで前日のまま。ホーム表示またはコールド起動で更新される。
- 実機検証前にマージしない。Issueの完了判断には本人による操作感と回帰の確認が必要。
